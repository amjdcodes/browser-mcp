> **المصدر:** `docs/browser-tool-feedback.md` (تقرير تجربة عملية) + `docs/browser-tool-verification-report.md` (تقرير تحقق ومراجعة مصدر).
> **المنهجية:** قراءة التقريرين، ثم مطابقة كل ادعاء بالكود المصدري الفعلي، ثم تحديد السبب الجذري والإصلاح المقترح لكل مشكلة.

## 1. نطاق العمل

مراجعة 10 مشكلات وردت في تقرير التجربة الأول، والتحقق منها عبر تقرير التحقق الثاني، ثم إسقاطها على الكود:

- `src/viewport.js` — إعدادات المقاسات والتحقق منها.
- `src/utils.js` — القيود والتحقق الأمني وبوّابة `evaluate`.

## 3. الإصلاحات المؤكدة (تنفيذ مباشر)

### خطة 3 — إصلاح تشوّه لقطة `full_page` مع RTL والعناصر الثابتة

**السبب الجذري المؤكَّد**
عند `full_page` يُعاد ضبط ارتفاع منطقة العرض على **ارتفاع المستند الكامل** قبل الالتقاط:

```js
// index.js:649-655
await browser.send('Emulation.setDeviceMetricsOverride', {
  width: visualViewport.clientWidth,
  height: Math.max(fullPageClip.height, visualViewport.clientHeight), // = ارتفاع المستند
  deviceScaleFactor: 1, mobile: false
});
```

عندما يصبح ارتفاع منطقة العرض = ارتفاع المستند، تتمدد العناصر ذات `position:fixed` (الدرج/القائمة الجانبية) مع `height:100%` لتمتد على طول الصورة كله وتغطي المحتوى، وينضغط التخطيط في عمود ضيق — وهو بالضبط ما وُصف في التقرير (صورة بعرض `1425` والفراغ على الجهة المقابلة في RTL).

**الإصلاح المقترح (الخيار المفضّل)**
1. **عدم توسيع منطقة العرض إلى ارتفاع المستند.** أبقِ ارتفاع منطقة العرض كما هو (قياسي)، واستخدم تقنية Chromium الأصلية للقطات ما بعد الإطار:
   - استدعِ `Page.captureScreenshot` مع `clip = {x:0, y:0, width: contentSize.width, height: contentSize.height, scale}` و`captureBeyondViewport: true` دون تغيير أبعاد العرض.
   - هذا يمنع تمدّد العناصر الثابتة لأنها تُرسم مرة واحدة عند موضعها الطبيعي، ويحافظ على حلّ التخطيط كما يراه المستخدم فعلاً.
2. **طبقة أمان إضافية للعناصر الثابتة** (إن ظهر تكرار لها مع `captureBeyondViewport`): قبل الالتقاط فقط، أدخل عبر `Runtime.evaluate` عنصر `<style id="__mcp_fullpage_fix">` يثبّت العناصر الثابتة:
   ```css
   * { position: fixed !important; position: absolute !important; }
   /* أو تثبيتها في أعلى الصورة بدل حذفها */
   ```
   ثم أزل هذا العنصر في `finally` (بنفس نمط استرجاع المنفذ الحالي).
3. **مراجعة نقطة أصل التخطيط في RTL** بعد الإصلاح للتأكد من عدم انعكاس الإزاحة الأفقية.

**بديل أدقّ (إن لزم):** تثبيت كل عنصر ثابت في موضعه الحالي بتحويله إلى `position:absolute` مع `top = rect.top + scrollY` بدل حذفه، لتظهر الطبقات مرة واحدة دون فقدانها.

**معايير القبول**
- لقطة `full_page` على صفحة RTL ذات عنصر ثابت: لا تمدّد لعمود ضيق، ولا تغطية كاملة من الدرج الثابت، والعناصر الثابتة تظهر مرة واحدة.
- اللقطات غير الكاملة تبقى سليمة دون تغيير.
- استرجاع المنفذ (`browser.viewport`) بعد الالتقاط يبقى مضموناً عبر `finally`.

**الاختبار:** إضافة/توسيع اختبار في `tests/screenshot-limits.test.js` أو `tests/resize.test.js` يستخدم صفحة `dir="rtl"` فيها عنصر `position:fixed; height:100%`، ويتحقق من قياسات الصورة الناتجة وعدم انضغاط العرض.

### خطة 4 — السماح بالتمرير بقيمة `y` وحدها

**السبب الجذري**
```js
// index.js:1155
if (hasPosition && (x === undefined || y === undefined)) {
  return formatToolError(toolError('INVALID_ARGS',
    'Both x and y must be provided for coordinate scrolling'));
}
```

**الإصلاح المقترح**
- إلغاء الشرط الإلزامي، والتعامل مع الإحداثي الناقص كـ«أبقِ الموضع الحالي» لا كصفر.
- تعديل `IN_PAGE.scrollToPosition` في `src/helpers.js:76–79` ليقبل `x`/`y` بقيمة `null`:
  ```js
  window.scrollTo({
    top: y == null ? window.scrollY : y,
    left: x == null ? window.scrollX : x,
    behavior: 'instant'
  });
  ```
- إبقاء `browser_scroll({direction, ...})` كبديل موثّق دون تغيير.

**معايير القبول**
- `browser_scroll({y: 600})` ينجح ويمرّر رأسياً دون تغيير الإحداثي الأفقي.
- `browser_scroll({x: 300})` يعمل بالمثل.
- الوضعان المتنازعان (اتجاه + إحداثيات) يبقيان مرفوضين برسالة `INVALID_ARGS` واضحة.

**الاختبار:** توسيع تغطية `browser_scroll` في `tests/interaction.test.js`.

### خطة 7 — تصحيح امتداد ملف اللقطة

**السبب الجذري**
```js
// index.js:538-542
const ext = format === 'jpeg' ? JPEG_EXTENSIONS : PNG_EXTENSIONS;
const hasExt = ext.some(e => filename.toLowerCase().endsWith(e));
if (!hasExt) filename = `${filename}.${format === 'jpeg' ? 'jpg' : 'png'}`;
```
`01-hero.png` مع الصيغة الافتراضية `jpeg` لا يُعدّ مطابقاً لامتدادات JPEG، فيُضاف `.jpg` → `01-hero.png.jpg`.

**الإصلاح المقترح**
- تجزئة الاسم دائماً: إن انتهى باسم صورة معروف (`.png/.jpg/.jpeg/.webp`) **استبدله** بامتداد الصيغة المطلوبة بدل إضافته:
  - `01-hero.png` + `format=jpeg` → `01-hero.jpg`
  - `shot-format` + `format=png` → `shot-format.png`
- توثيق السلوك صراحةً في README: «الامتداد يُحسم من `format`، ويُستبدل أي امتداد صورة سابق».

**معايير القبول**
- لا يوجد أي مسار ناتج بامتداد مزدوج.
- المسار المُعاد يطابق الامتداد الفعلي للمحتوى (JPEG/PNG).

### خطة 9 — إضافة قراءة عنوان URL

**السبب الجذري**
13 أداة مسجّلة لا يوجد بينها `browser_get_url`، و`browser_click`/`browser_press` لا تعيدان العنوان بعد التفاعل.

**الإصلاح المقترح**

2. (اختياري لكن مفيد) إضافة `url` إلى نتيجة `browser_click` عند حدوث انتقال.
3. تحديث التوثيق من 13 أداة إلى 14 في `README.md` و`ARCHITECTURE.md`.

**معايير القبول**
- يمكن معرفة الصفحة الحالية دون `evaluate` ودون `get_text`.
- الأداة قراءة فقط وغير مقفلة (read-only).

**الاختبار:** إضافة اختبار في `tests/reading-tools.test.js`.

### خطة 10 — تكبير المقاس الافتراضي

**السبب الجذري**
`DEFAULT_FLAGS` في `src/browser.js:18–41` لا تتضمّن `--window-size`، فيُستخدم مقاس Chromium الافتراضي الضيق (`780×437`)، وهو أصغر من نقاط انكسار شائعة.

**الإصلاح المقترح**
- إضافة `'--window-size=1440,900'` إلى `DEFAULT_FLAGS`.
- إبقاء `preset: desktop` كما هو (`1280×800 @1`) أو ترقيته اختيارياً إلى `1440×900` — قرار منفصل قابل للنقاش.
- ملاحظة: هذا يؤثر على اللقطة الأولى قبل أي `browser_resize`؛ لا يتعارض مع `Emulation.setDeviceMetricsOverride`.

**معايير القبول**
- أول لقطة قبل أي resize تُظهر تخطيط سطح المكتب لا التخطيط الجوّالي.

## 4. الإصلاحات الجزئية / التصميمية (تحتاج قراراً)

### خطة 5 — توضيح دلالة `inViewport`

**السبب الجذري**
`IN_PAGE.isInViewport` (`helpers.js:82–88`) تُعيد `true` فقط إذا كان العنصر **ظاهراً بالكامل** داخل النافذة. و`scrollIntoView` يستخدم `block:'center'`، فأي عنصر أطول من النافذة يمتد خارجها → `false` دائماً حتى بعد تمرير ناجح.

**الإصلاح المقترح**
- إبقاء `inViewport` بمعنى «أي جزء ظاهر» (كما يفهمه المستدعي عادةً)، وإضافة حقل دقيق:
  - `fullyInViewport` (الظهور الكامل الحالي)، و/أو
  - `visibleRatio` (نسبة مساحة التقاطع)، و`boundingBox` والمسافة المتبقية للتمرير.
- بديل أقل تغييراً: إبقاء القيمة كما هي وتوثيق التعريف في README (لكن هذا لا يعالج الالتباس).
- أي تغيير في الدلالة يجب أن يُرافق تحديث `tests/interaction.test.js:746,975`.

### خطة 6 — `mobile:true` والقيم «المتناقضة»

**السبب الجذري (أدق من التقرير الأول)**
1. `browser_resize` يعيد القيم **المطلوبة (صدى)** لا المقيسة:
   ```js
   // index.js:1290-1303
   width: viewport.width, height: viewport.height ...
   ```
2. محاكاة الجوال تُفعّل الانكماش ليلائم العرض (shrink-to-fit)؛ فإذا كانت الصفحة فيها تجاوز أفقي (كما في صفحة الاختبار: `.filters` بعرض 712 داخل 390) يصبح `innerWidth` بعرض المحتوى لا بعرض الجهاز، مع `scrollX` سالب.

**الإصلاح المقترح**
- بعد تطبيق المنفذ، قِس القيم الفعلية عبر `Runtime.evaluate` (`innerWidth`, `innerHeight`, `devicePixelRatio`, `scrollX`, `documentElement.scrollWidth`) وأعد الحقلين:
  - `requested: {width, height}` و`measured: {innerWidth, innerHeight, dpr, scrollX}`.
- إضافة تحذير عند عدم تطابق `innerWidth` مع العرض المطلوب (مؤشر على تجاوز أفقي أو shrink-to-fit).
- توثيق فرق `mobile:true` مقابل `mobile:false`.

**معايير القبول**
- لا تُوهم النتيجة بالتطابق؛ القيم المقيسة متاحة صراحةً.

### خطة 1 — `evaluate` معطّلة افتراضياً (قرار تصميمي)

**الواقع في الكود**
`isEvalJsEnabled()` (`utils.js:173–176`) افتراضها `false`، والحارس في `index.js:1324–1329` يرفض بـ`EVAL_DISABLED`. ملف `.env` المحلي في هذا المستودع يضبط `ENABLE_EVAL_JS=1`، بينما `.env.example` يوثّق `false`.

**التوصية**
- **عدم قلب الافتراضي** (بوّابة أمنية موثّقة ضد SSRF وقراءة الكوكيز — راجع `ARCHITECTURE.md` قسم Security Model).
- بدلاً من ذلك تحسين **قابلية الاكتشاف**:
  - إظهار حالة `evaluate` ضمن نتيجة `browser_snapshot` أو قائمة الأدوات (مثلاً `evaluateEnabled: false`)،
  - وإضافة رسالة إرشاد واضحة عند الرفض توضّح أنها معطّلة عمداً وكيفية تفعيلها، مع التنبيه الأمني.
- توثيق أن هذا قرار وعي لا عطل.

### خطة 2 — فقدان حالة الجلسة عند الانهيار

**الواقع في الكود**
`_handleCrash()` (`browser.js:390–417`) يستدعي `cleanup()` ثم `start()`، و`start()` ينشئ **مجلد ملف تعريف جديد** (`mkdtempSync` في `browser.js:118`) ويبدأ على `about:blank`، كما أن `cleanup()` يحذف الملف القديم (`browser.js:511–528`). النتيجة: ضياع `localStorage` وموضع التمرير. ولا يوجد أي حقل `sessionReset`/`retryable` في الكود (تأكدنا بالبحث).

**ملاحظة مهمة**
رسالة `Connection error. Type "continue" ... Trace ID` **ليست من هذا السيرفر** — هي من عميل CommandCode، فلا تُعالَج في هذا المستودع.

**الإصلاح المقترح (داخل نطاق السيرفر)**
1. **الحفاظ على ملف التعريف عند إعادة التشغيل بعد الانهيار:** مرّر `profileDir` القائم إلى `start()` بدلاً من إنشاء مجلد جديد، فلا يُحذف إلا عند `cleanup()` النهائي/الإغلاق. هذا يحفظ `localStorage` وحالة الصفحة قدر الإمكان.
2. **إشارة صريحة للعميل:** إضافة `sessionReset: true` إلى نتيجة أول استدعاء بعد إعادة التهيئة، وتغليف أخطاء الاتصال القابلة لإعادة المحاولة بـ`retryable: true`.
3. إعادة محاولة تلقائية واحدة عند فشل CDP العابر (بحذر، مع تجنّب الحلقة).

**معايير القبول**
- بعد إعادة تشغيل ناتجة عن انهيار، يُبلَّغ العميل صراحةً بإعادة التهيئة، وتُحفظ بيانات الملف الشخصي ما أمكن.

**الاختبار:** توسيع `tests/restart.test.js` و`tests/reconnect.test.js`.

## 5. تصحيحات على دقة التقريرين (لا تتطلب تعديل كود)

هذه ادعاءات وردت في أحد التقريرين ونفتها مطابقة الكود — يُستحسن تصحيح التقرير نفسه:

1. **`browser_click` مع `force` يُعيد `forced` فعلاً.** الكود يعيده (`index.js:1018` و`helpers.js:676`)، وREADME يوثّقه (`README.md:358`)، ويوجد اختبار يتحقق منه (`tests/interaction.test.js:842`). لذا بند «عدم إرجاع `forced`» في تقرير التحقق **غير صحيح** مقابل الكود الحالي.
2. **`matchesHover` تشخيصي فقط** (لا يؤكد تفعّل تأثير CSS): `helpers.js:246–249` يعيد `element.matches(':hover')`، والREADME يصفه بدقة (`README.md:419`).
3. **`snapshot` لا يعيد `selector` لكل عنصر** — فقط عند وجود `id`/`name`/`aria-label`/`placeholder` أو نتيجة بحث بديلة (`index.js:845–931`).
4. **`get_text` يقرأ النص حتى وهو غير مرئي** (`opacity:0`) لأنه يقرأ DOM لا الرؤية — فلا أساس لادعاء فشله على الإشعار.
5. **اللقطة تُعيد أبعاداً مقيسة فعلاً** (`width/height/scale/measured` — `index.js:722–732`) لكن **لا تُعيد `scrollX/scrollY`**؛ اقتراح التقرير بإضافتهما ما زال قائماً.
6. **الرسالة `Connection error ... Trace ID` من العميل لا السيرفر** (تأكد بتقرير التحقق).
